# 仲裁池三输出与仲裁费 v4 硬切换施工单

## 1. 施工结论

本次迭代采用一次性破坏性升级，把仲裁池状态交易从两个资金输出升级为三个固定资金输出：

```text
output[0] = Buyer
output[1] = Seller
output[2] = Arbiter
output[3] = 可选付款证明（OP_FALSE OP_RETURN）
```

`output[2]` 在仲裁池初始状态中必须存在，锁定到 Arbiter 的 P2PKH 脚本，金额固定为 `0`。后续状态使用显式的 `arbiterAmount` 分配仲裁费；它表示当前状态中分配给 Arbiter 的绝对金额，不表示相对上一状态的增量。

TypeScript、Go、Rust 必须在同一次施工中切换到同一套 v4 协议、相同字段语义、相同输出顺序、相同手续费算法、相同交易序列化和相同签名字节。这里的“保持兼容”只表示三种语言的 v4 实现相互兼容，不表示兼容 v3 状态交易或 v3 API。

本次升级不保留以下兼容路径：

- 不接受只有 `[Buyer, Seller]` 两个资金输出的 v3 仲裁状态。
- 不根据输出数量自动猜测 v3/v4。
- 不把旧 `output[2]` 猜测为 Arbiter 或付款证明。
- 不保留缺少 `arbiterAmount` 的旧状态构建 API。
- 不按 v3 重新签名、重试或降级。
- 不保留 `/v3` Go module、v3 fixture、旧协议别名或旧函数转发层。

协议和三个包的目标版本统一为：

```text
Protocol        = "bitfs.pool.v4"
ProtocolVersion = 4
ReleaseVersion  = "4.0.0"
Go module       = github.com/bsv8/MultisigPool/v4
Go tag          = v4.0.0
Rust tag        = rust-v4.0.0
```

## 2. 现状与必须一起修复的差异

### 2.1 TypeScript

当前 `src/arbitrated_pool/state.ts` 只创建 Buyer、Seller 两个资金输出；可选付款证明占用 `output[2]`。`ArbitratedPoolStateInput` 没有 `arbiterAmount`，Buyer 金额只扣除 Seller 金额和手续费，因此无法表达给 Arbiter 付款。

当前状态校验允许输出数量为 `2` 或 `3`，但只校验前两个输出脚本。升级后必须改为校验三个资金输出及可选的第四个数据输出。

### 2.2 Go

当前 `pkg/arbitrated_pool/state.go` 明确声明固定输出为 `[Buyer, Seller]`，`StateInput` 没有 `ArbiterAmount`，脚本辅助函数也只返回 Buyer、Seller 的 P2PKH 脚本。可选付款证明同样占用 `output[2]`。

Go 的 `BuyerAmount uint64` 当前以 `0` 同时表示“调用方未提供校验值”和“Buyer 的期望金额为 0”，语义不完整。本次破坏性升级必须改为 `*uint64`，用 `nil` 表示不校验，用非空指针表示必须精确匹配，包括显式校验金额为 `0`。

### 2.3 Rust

当前 `rust/` crate 只提供通用多签数据结构和简化签名逻辑，没有仲裁池的角色、建池、状态构建、验签和三种签名合并公共 API。当前 Rust/Go 示例比较的是两方池，文档中也明确承认 Rust 不参与仲裁池业务交易的字节比较。

当前 `rust/src/multisig.rs` 的签名哈希不是仲裁池所需的完整 BIP143/FORKID 实现，交易输入类型也没有携带源输出金额和锁定脚本。不能用该简化实现宣称三语言仲裁池兼容。

本次施工必须把 Rust 提升为完整的仲裁池协议实现，并让它独立构造和签署与 TypeScript、Go 完全相同的 v4 状态交易。

### 2.4 版本与交叉测试

当前版本同步程序、Go module、源码导入路径、文档和 fixture 均固定为 v3。现有 `examples/arbitrated_pool_compare` 只比较 Go 和 TypeScript；现有 `examples/rust_go_comparison` 只覆盖两方池。

本次不得只更新常量而漏改 module path、fixture 或发布版本，也不得只让 Rust 读取另外两种语言生成的 hex 后做字段检查。

## 3. v4 仲裁池协议不变量

### 3.1 角色顺序

2-of-3 锁定脚本的公钥顺序继续固定为：

```text
[Buyer, Seller, Arbiter]
```

门限继续固定为 `2`。三个公钥必须存在、有效、使用压缩编码进行协议比较，并且互不相同。

角色顺序本身不变，但新增 Arbiter 资金输出会改变状态交易字节、交易 ID、签名哈希、三种角色签名和三种合并结果。

### 3.2 固定资金输出

所有 v4 仲裁池状态必须至少有三个输出：

| 索引 | 类型 | 锁定对象 | 金额语义 |
| --- | --- | --- | --- |
| `0` | P2PKH | Buyer | 池金额扣除 Seller、Arbiter 和本状态链上手续费后的余额 |
| `1` | P2PKH | Seller | `sellerAmount`，当前状态分配给 Seller 的绝对金额 |
| `2` | P2PKH | Arbiter | `arbiterAmount`，当前状态分配给 Arbiter 的绝对金额 |
| `3` | 数据输出，可选 | `OP_FALSE OP_RETURN` | 金额必须为 `0`，承载付款证明原始字节 |

前三个资金输出的位置和脚本不得因金额为 `0` 而省略、排序或合并。初始状态必须包含 `output[1] = 0` 和 `output[2] = 0`。

“三个输出”在本协议中准确指三个固定资金输出；存在付款证明时，交易总输出数为四个。

### 3.3 金额公式

状态构建必须使用以下显式数据流：

```text
allocatedAmount = sellerAmount + arbiterAmount
buyerBeforeFee  = poolAmount - allocatedAmount
stateFee        = ceil(serializedSizeWithFake2Of3UnlockingScript * feeRate / 1000)
buyerAmount     = buyerBeforeFee - stateFee
```

最终必须满足：

```text
buyerAmount + sellerAmount + arbiterAmount + stateFee = poolAmount
```

可选付款证明输出金额为 `0`，不参与资金分配。

三种语言必须先执行无溢出的 `sellerAmount + arbiterAmount` 校验，再与 `poolAmount` 比较。不得先做可能回绕的整数加法，也不得用浮点数计算手续费。

### 3.4 仲裁费语义

- `arbiterAmount` 是状态的必填协议字段。
- 开池状态由库内部显式传入 `arbiterAmount = 0`。
- 后续每个状态由协商方显式给出新的绝对金额。
- 允许 `arbiterAmount` 保持不变、增加或减少；协议不猜测业务协商过程。
- 2-of-3 的任意合法两方签名都能批准该状态，`SIGHASH_ALL | SIGHASH_FORKID` 必须绑定三个资金输出和可选付款证明。
- 库不自动计算“仲裁服务价格”，不按比例抽成，也不从 Seller 金额中隐式扣款。

### 3.5 付款证明位置

付款证明从 v3 的 `output[2]` 固定迁移到 v4 的 `output[3]`：

- 没有付款证明时，状态恰好有三个输出。
- 新增付款证明时，在索引 `3` 添加金额为 `0` 的 `OP_FALSE OP_RETURN` 输出。
- 更新付款证明时，只替换索引 `3`，不得覆盖 Arbiter 输出。
- 调用方未提供新付款证明时，沿用上一状态已有的索引 `3`；空值不是删除指令。
- 已有第四输出必须严格验证为金额 `0` 且脚本是本项目支持的付款证明格式。
- 不接受第五个输出或任意未知附加输出。

## 4. 状态构建与校验顺序

三种语言的实现顺序必须等价，以避免一种语言在手续费计算前后采用不同交易结构：

1. 校验 `protocol`、`version`、角色、公钥和所有整数输入。
2. 克隆或从 raw transaction 解析调用方提供的上一状态，不修改调用方对象或字节。
3. 要求恰好一个输入，并要求上一状态为三个固定资金输出加零或一个付款证明输出。
4. 校验输入 sequence 严格增加。
5. 校验源输出存在，其金额等于 `poolAmount`，锁定脚本等于 `[Buyer, Seller, Arbiter]` 的 2-of-3 P2MS。
6. 校验 `output[0..2]` 分别锁定到 Buyer、Seller、Arbiter；如有 `output[3]`，严格校验付款证明结构。
7. 无溢出地校验 `sellerAmount + arbiterAmount <= poolAmount`。
8. 写入三个资金输出的脚本和手续费前金额，写入新的 sequence 和可选 lock time。
9. 如提供非空付款证明，在索引 `3` 添加或替换付款证明。
10. 临时写入两个签名位的假解锁脚本，按最终输出结构计算序列化大小和手续费。
11. 从 Buyer 输出扣除手续费；余额不足立即失败。
12. 如调用方提供 `buyerAmount`，要求它与规范计算结果完全一致。
13. 清空解锁脚本并返回新的未签名状态。

任何错误必须立即暴露，不得修正输出顺序、截断金额、删除未知输出、猜测源输出或改用默认手续费。

## 5. 公共 API 设计

### 5.1 TypeScript

`ArbitratedPoolStateInput` 修改为：

```ts
export interface ArbitratedPoolStateInput {
  readonly protocol: string;
  readonly version: number;
  readonly previousState: Transaction;
  readonly sequence: number;
  readonly lockTime?: number;
  readonly buyerAmount?: number;
  readonly sellerAmount: number;
  readonly arbiterAmount: number;
  readonly poolAmount: number;
  readonly roles: ArbitratedPoolRoles;
  readonly feeRate: number;
  readonly paymentProof?: Uint8Array | number[] | null;
}
```

要求：

- `sellerAmount`、`arbiterAmount`、`poolAmount`、`sequence`、`lockTime`、`buyerAmount` 必须按各自语义校验为安全整数。
- `sellerAmount`、`arbiterAmount` 不得为负数。
- `buildArbitratedPoolOpeningState` 的公开参数保持不变，但内部创建三个资金输出，并以 `arbiterAmount: 0` 调用统一状态构建函数。
- `buildArbitratedPoolState` 与 `buildArbitratedPoolFinalState` 不得为缺失的 `arbiterAmount` 填 `0`。
- 输出脚本辅助纯函数返回 `{ buyer, seller, arbiter }`，状态变化通过克隆后的新交易显式传递。

### 5.2 Go

`StateInput` 至少修改为：

```go
type StateInput struct {

    Version              uint32
    PreviousRawTx        []byte
    PreviousSourceOutput *transaction.TransactionOutput

    LockTime             *uint32
    BuyerAmount          *uint64

    ArbiterAmount        uint64
    PoolAmount           uint64
```

要求：

- `BuyerAmount == nil` 表示不执行调用方期望值校验；非空时必须精确比较，包括期望值为 `0`。
- `ArbiterAmount` 不使用额外哨兵值，`0` 是合法且明确的协议金额。
- `scripts` 辅助函数返回 multisig、Buyer、Seller、Arbiter 四个脚本，且不修改共享状态。
- 所有加减法先做边界判断，禁止依赖 `uint64` 回绕。
- `BuildArbitratedPoolOpeningState` 固定添加 Arbiter 零金额输出。
- Go API 不保留旧 `StateInput` 别名或缺字段构造器。

- 原生 Rust API 与 WASM 暴露层复用同一组纯业务函数，WASM 层只负责数据转换和错误映射。

- 签名必须使用确定性 RFC6979、规范 DER、low-S 和 `SIGHASH_ALL | SIGHASH_FORKID`，不得继续使用当前简化的全交易拼接哈希冒充池协议签名。
- 如引入交易依赖，只允许固定、可发布、可由 `Cargo.lock` 锁定的依赖；不得让发布 crate 依赖未固定 Git 分支。
- 所有错误对外使用英文；源码注释和文档使用中文。

## 6. 签名、验签与合并规则

签名入口的名称和角色含义保持不变，但签名对象切换为 v4 三资金输出状态。

必须保持以下规则：

- 签名前要求状态只有一个输入且解锁脚本为空。
- 必须显式绑定源输出的金额和 2-of-3 锁定脚本。
- 必须校验私钥与所声明角色的公钥一致。
- Buyer、Seller、Arbiter 三个单签必须分别可验。
- 合并前必须分别验签，并拒绝重复签名。
- 合并顺序必须符合 `[Buyer, Seller, Arbiter]` 公钥顺序下的 CHECKMULTISIG 要求。
- 三种合法组合均必须支持：Buyer+Seller、Buyer+Arbiter、Seller+Arbiter。
- `SIGHASH_ALL` 必须使任何 `sellerAmount`、`arbiterAmount`、输出脚本、付款证明、sequence 或 lock time 改动导致旧签名失效。
- 签名与合并函数不得修改调用方传入的未签名状态。

## 7. 手续费一致性

新增 Arbiter P2PKH 输出后，状态交易尺寸和手续费会改变。三种语言必须以同一份最终未签名结构加同一份两个 73 字节签名位的假解锁脚本估算大小。

手续费公式固定为整数运算：

```text
(size * feeRate + 999) / 1000
```

要求：

- `feeRate` 的协议单位统一为 `sat/KB` 的非负整数。
- `feeRate = 0` 时手续费为 `0`，不得强制最小手续费。
- 乘法与加 `999` 前必须检查溢出。
- 付款证明存在时，其完整脚本长度必须计入费用。
- 手续费只能从 Buyer 输出扣除。
- `sellerAmount + arbiterAmount == poolAmount` 但仍需支付正手续费时，必须返回 Buyer 余额不足错误。

Funding 交易的结构和资金池 P2MS 脚本不因第三个状态输出而改变，但其 API 元数据、协议版本、包路径和所有 v4 fixture 必须同步更新。

## 10. 单元测试要求

### 10.1 三种语言共同覆盖

每种语言都必须独立覆盖：

- 开池状态恰好有三个资金输出。
- 开池状态 `output[2]` 锁定 Arbiter 且金额为 `0`。
- Seller 非零、Arbiter 为零的普通状态。
- Seller 和 Arbiter 均非零的仲裁费状态。
- Buyer 金额严格等于规范公式。
- 三个资金输出加手续费严格等于池金额。
- 付款证明只出现在 `output[3]`，并计入手续费。
- 上一状态已有付款证明且新输入未提供证明时，证明保持不变。
- 更新付款证明不会覆盖 Arbiter 输出。
- Seller 与 Arbiter 金额之和大于池金额时失败。
- 分配金额恰好耗尽池金额但 Buyer 无法支付正手续费时失败。
- 整数溢出边界失败。
- 两输出 v3 状态失败。
- 三输出但第三个脚本不是 Arbiter P2PKH 时失败。
- 第四输出不是零金额付款证明时失败。
- 第五输出失败。
- sequence 未增加失败。
- 源输出缺失、金额错误、脚本错误或角色错位失败。
- 调用方提供的 `buyerAmount` 与规范结果不一致时失败，包括显式期望 `0`。
- 状态构建、签名和合并不修改调用方输入。
- 三个角色单签均可验证，三种两两组合均可合并。
- 修改 Arbiter 金额后旧签名失效。
- 修改付款证明后旧签名失效。
- 错误消息为英文。

### 10.2 TypeScript 特有边界

- 拒绝非安全整数、`NaN`、`Infinity`、负数和小数金额。
- 编译期要求 `arbiterAmount`；另用运行时测试证明来自非类型调用方的缺字段输入会失败。
- raw serialization 后仍保持三个资金输出顺序。

### 10.3 Go 特有边界

- `BuyerAmount == nil` 与 `BuyerAmount = pointer(0)` 的语义分别测试。
- `uint64` 加法、乘法和手续费上取整的溢出分别测试。
- 标准 raw transaction 通过显式 `PreviousSourceOutput` 恢复源输出，冲突元数据必须失败。

### 10.4 Rust 特有边界

- raw hex 解析和重新序列化逐字节一致。
- BIP143 中 `hashPrevouts`、`hashSequence`、`hashOutputs`、源脚本和源金额分别用确定向量测试。
- native Rust 与 WASM 包装层对相同输入产生相同结果。
- 不再保留只检查“脚本非空”就宣称跨语言成功的测试。

## 11. 文档与示例行为

所有公开文档和示例统一说明：

- 仲裁池状态资金输出为 `[Buyer, Seller, Arbiter]`。
- Arbiter 初始金额为 `0`，但输出不能省略。
- 后续通过绝对 `arbiterAmount` 协商仲裁费。
- 付款证明存在时位于第四个输出。
- v3 状态和 v3 签名不能交给 v4 API 使用。
- 三种两两签名组合都能批准包含仲裁费的完整状态。

online/offline 示例至少增加一个非零仲裁费流程，并打印三个角色金额。示例不得广播真实交易作为测试门禁的一部分。

历史施工单 `001`、`002` 中关于 v3、`[Buyer, Seller]` 仲裁输出和“协议字节不变”的结论必须标注已被本施工单取代，避免仓库同时存在两套现行规范。

## 15. 最终验收清单

### 15.1 协议结构

- [ ] 所有 v4 仲裁开池状态恰好包含 Buyer、Seller、Arbiter 三个资金输出。
- [ ] Arbiter 初始输出存在、脚本正确且金额为 `0`。
- [ ] 非零 `arbiterAmount` 能生成正确状态，且不改变角色顺序。
- [ ] 付款证明只位于可选 `output[3]`，不会覆盖 Arbiter 输出。
- [ ] 两输出 v3 状态和未知附加输出均立即失败。

### 15.2 金额与手续费

- [ ] 三种语言使用相同的绝对 `sellerAmount`、`arbiterAmount` 语义。
- [ ] Buyer、Seller、Arbiter、手续费严格守恒。
- [ ] 新增 Arbiter 输出和可选证明都进入规范手续费估算。
- [ ] 所有整数溢出、负数、小数和余额不足路径按语言能力严格失败。
- [ ] Go 的可选 Buyer 期望金额不再使用 `0` 哨兵。

### 15.3 签名安全

- [ ] Buyer、Seller、Arbiter 单签均为真实 BIP143/FORKID 签名。
- [ ] 三种两两组合均可验签和合并。
- [ ] 修改 Arbiter 金额或付款证明会使旧签名失效。
- [ ] 三种语言的签名 DER 字节和合并交易完全相同。
- [ ] Rust 不再用简化哈希宣称仲裁池协议兼容。

### 15.4 三语言兼容

- [ ] TypeScript、Go、Rust 独立消费同一 v4 fixture 原始输入。
- [ ] 三者的锁定脚本、funding、三类状态、txid、单签和合并交易逐字节相同。
- [ ] Rust runner 调用发布 crate 的公开 API，而非复制示例实现。
- [ ] 任一语言缺失或失败都会使完整门禁失败。
- [ ] 两方池交叉测试在统一 v4 版本线上继续通过。

### 15.5 版本与清理

- [ ] 协议和三个包统一为 v4/4.0.0。
- [ ] Go module 和全部 import 统一为 `/v4`。
- [ ] v3 fixture、v3 回退、旧输出猜测和兼容别名均已删除。
- [ ] 当前文档不存在“Arbiter 不参与资金输出”的有效规范。
- [ ] 版本生成文件、锁文件和发布标签规则与清单一致。

### 15.6 工程质量

- [ ] 状态构建以纯函数和显式数据流组织，不修改调用方交易或共享状态。
- [ ] 文档与注释为中文，对外错误消息为英文。
- [ ] 不存在静默修正、自动降级、默认仲裁费、隐式输出迁移或失败后重试。
- [ ] `scripts/run_all_tests.sh`、`git diff --check` 和版本一致性检查全部通过。

## 16. 完工判定

只有当第 15 节全部满足，且 TypeScript、Go、Rust 能从同一份原始 fixture 独立构造出完全相同的 v4 仲裁池交易、签名和三种合并结果时，本施工才算完成。

以下情况均不算完成：

- 只多创建一个金额为 `0` 的 Arbiter 输出，但 API 仍不能传入非零仲裁费。
- Go 和 TypeScript 已支持三输出，Rust 仍只验证通用多签或读取现成 hex。
- 三种语言解析出的金额相同，但 raw transaction、txid 或签名字节不同。
- 付款证明仍可能覆盖 Arbiter 输出。
- v4 API 仍接受两个资金输出的 v3 状态。
- package 版本已升级，但协议常量、Go module、fixture 或文档仍停留在 v3。
- 为通过测试而加入输出猜测、版本回退、默认金额或其他兜底逻辑。
