# 统一版本清单与三语言发布施工单

## 1. 施工结论

本次迭代采用一次性硬切换：建立一个版本事实源，只保留一个公开发布入口，同时发布 TypeScript/npm、Go module 和 Rust crate。

统一版本线意味着三个语言包必须使用同一个 SemVer；同时必须把包发布版本与协议校验版本明确区分：

- 协议标识：`bitfs.pool.v3`。
- 协议版本：整数 `3`，参与交易协议校验，普通包发布不得修改。
- npm 发布版本：当前为 `3.0.0`。
- Go module 发布版本：当前为 `3.0.0`，Git tag 为 `v3.0.0`，module path 固定为 `/v3`。
- Rust crate 发布版本：当前为 `3.0.0`，与 npm、Go 保持统一版本线。

版本清单是唯一可人工修改的版本来源。`package.json`、`Cargo.toml`、Go/TypeScript 公开常量和锁文件中的版本均为必须同步、必须校验的镜像，不再允许分别手工维护。

只保留一个公开发布入口：

```bash
scripts/release-all.sh
```

旧的 npm、Go、all 三套独立发布脚本全部删除，不保留转发脚本、兼容入口、交互式版本选择、默认版本、自动猜测版本或失败后换版本重试。

## 2. 简述缘由

当前仓库曾同时存在以下相互独立的版本来源：

- `package.json` 的 npm 版本。
- `pkg/index.go` 的 Go 发布版本。
- Go module path 和 Git tag 主版本。
- `rust/Cargo.toml` 的 crate 版本。
- Go、TypeScript 子包中的协议版本常量。
- 发布脚本交互输入的新版本。

这会产生两类高风险错误：

1. 把发布版本 `3.0.0` 当成交易协议版本 `3`，导致公共 API 类型或协议校验不一致。
2. npm、Go tag、Rust crate 只发布其中一部分，或者包已发布但仓库没有对应提交和 tag。

本次施工的目标不是增加更多同步约定，而是把版本输入收敛到一个文件，把所有发布动作收敛到一个入口，并让任何不一致在第一次外部发布前暴露。

## 3. 版本模型

### 3.1 唯一事实源

新增：

```text
release/versions.json
```

固定结构如下：

```json
{
  "schemaVersion": 1,
  "protocol": {
    "id": "bitfs.pool.v3",
    "version": 3,
    "goModuleMajor": 3
  },
  "packages": {
    "npm": "3.0.0",
    "go": "3.0.0",
    "rust": "3.0.0"
  }
}
```

字段约束：

- `schemaVersion` 只表示版本清单结构，不是协议版本或包版本。
- `protocol.id` 必须严格等于 `bitfs.pool.v3`。
- `protocol.version` 必须是正整数 `3`。
- `protocol.goModuleMajor` 必须是整数 `3`，并与 `go.mod` 的 `/v3` 一致。
- `packages.npm`、`packages.go`、`packages.rust` 必须是无 `v` 前缀的完整 SemVer。
- `packages.npm`、`packages.go` 与 `packages.rust` 必须完全相同，任何语言不得使用独立版本线。
- Go tag 由程序唯一推导为 `v${packages.go}`，不得另设可手工修改字段。
- Rust 源码追踪 tag 由程序唯一推导为 `rust-v${packages.rust}`。

### 3.2 协议版本与发布版本边界

必须保持以下公共含义：

```text
Protocol        = "bitfs.pool.v3"
ProtocolVersion = 3
Version         = ProtocolVersion
ReleaseVersion  = 对应语言包的发布版本
```

禁止：

- 使用字符串 `"3.0.0"` 校验交易协议。
- 使用整数 `3` 作为 npm、Go 或 Rust 的完整发布版本。
- 因为发布 `3.0.1` 而修改协议版本或 fixture 协议字段。
- 因为三个包使用 `3.x` 而把包版本字符串直接用于交易协议校验。
- 从 Git 最新 tag、registry 最新版本或默认值反推本次准备发布的版本。

## 4. 版本镜像与生成规则

### 4.1 Go

新增内部生成文件：

```text
internal/versioninfo/version.go
```

文件由版本同步程序生成，至少包含：

```go
const Protocol = "bitfs.pool.v3"
const ProtocolVersion uint32 = 3
const GoReleaseVersion = "3.0.0"
```

处理规则：

- `pkg/index.go` 只通过常量别名公开 `Protocol`、`ProtocolVersion`、`Version` 和 `ReleaseVersion`。
- `pkg/two_party_pool/index.go` 与 `pkg/arbitrated_pool/index.go` 使用同一个内部协议常量，不再各自维护数字 `3`。
- `go.mod` 的 module path 必须严格为 `github.com/bsv8/MultisigPool/v3`。
- 普通 patch/minor 发布不得自动改写 Go module path。
- 如将来升级到协议 v4，必须另立协议施工单，不得由本发布脚本自动完成。

### 4.2 TypeScript/npm

新增生成文件：

```text
src/version.ts
```

至少导出：

```ts
export const Protocol = 'bitfs.pool.v3' as const;
export const ProtocolVersion = 3 as const;
export const Version = ProtocolVersion;
export const ReleaseVersion = '3.0.0' as const;
```

处理规则：

- `src/types.ts` 从 `src/version.ts` 导入并重新导出协议常量，不再自行声明。
- `package.json.version` 必须等于 `packages.npm`。
- `package-lock.json` 根包版本必须等于 `packages.npm`。
- npm 产物的公开类型声明必须同时暴露正确的协议版本和发布版本。
- 不允许在运行时读取仓库路径下的 `release/versions.json`；发布包必须是自包含的编译结果。

### 4.3 Rust

处理规则：

- `rust/Cargo.toml` 的 `package.version` 必须等于 `packages.rust`。
- `rust/Cargo.lock` 中本项目 package 版本必须同步。
- Rust 对外协议常量必须来自同步生成的 Rust 源文件，或由检查程序严格验证为 `protocol.id` / `protocol.version`；不得把 crate 版本当协议版本。
- Rust crate tag 使用 `rust-v3.0.0` 形式，避免与 Go module 必需的 `v3.0.0` tag 冲突。

### 4.4 生成文件规则

- 生成文件必须带有“由版本同步程序生成，禁止手工修改”的中文注释。
- 生成结果必须确定：相同 `versions.json` 输入产生逐字节相同输出。
- 同步程序不得读取网络、Git tag 或环境变量决定版本。
- 同步程序不得在字段缺失时填默认值。
- 输入非法、目标文件结构异常、应替换字段出现零次或多次时必须用英文错误消息退出。
- 同步写入必须采用临时文件加原子替换，不能留下半写文件。

## 5. 版本同步程序

新增内部工具：

```text
scripts/release-versions.mjs
```

只提供两个明确动作：

```bash
node scripts/release-versions.mjs check
node scripts/release-versions.mjs sync
```

### 5.1 `check`

`check` 必须只读，并逐项验证：

- `versions.json` schema 和字段类型。
- 三个包版本的 SemVer 格式。
- npm、Go 与 Rust 统一版本线约束。
- `go.mod` 的 `/v3`。
- Go/TypeScript/Rust 协议常量。
- Go/TypeScript 发布版本常量。
- `package.json`、`package-lock.json`。
- `rust/Cargo.toml`、`rust/Cargo.lock`。
- 计划使用的 Go tag 与 Rust tag 可由清单唯一推导。

任何一项不一致都必须指出具体文件、期望值和实际值，并以非零退出码结束。

### 5.2 `sync`

`sync` 只把 `versions.json` 的值同步到允许的镜像文件，不做以下事情：

- 不修改协议业务代码。
- 不提交 Git。
- 不创建 tag。
- 不调用 registry。
- 不发布任何包。
- 不自动选择下一个版本。
- 不在错误时继续处理剩余文件。

同步完成后必须自动调用同一程序的 `check`；检查失败则整体失败。

实现应以纯函数组织：解析、校验、渲染和差异计算分别返回新值；文件写入集中在最外层，禁止用一个可变中心对象贯穿整个同步过程。

## 6. 唯一公开发布入口

新增：

```text
scripts/release-all.sh
```

删除：

```text
scripts/publish-npm.sh
scripts/publish-go.sh
scripts/publish-all.sh
```

`package.json` 只保留一个发布命令：

```json
{
  "scripts": {
    "release": "./scripts/release-all.sh"
  }
}
```

删除 `publish:npm`、`publish:go`、`publish:all`。不得保留隐藏入口或文档中的旧命令。

内部版本同步工具不属于发布入口；它不能对外发布或创建 tag。

## 7. 发布前置条件

`release-all.sh` 不接受交互式版本输入。它只发布 `release/versions.json` 明确声明的版本。

在任何外部写操作之前，必须依次验证：

1. Bash 严格模式为 `set -euo pipefail`。
2. 当前分支严格为 `main`；不是主分支直接失败，不允许人工确认后继续。
3. 工作树、暂存区和未跟踪文件均为空。
4. 当前 HEAD 已存在于 `origin/main`，不得发布仅存在于本机的提交。
5. `node scripts/release-versions.mjs check` 通过。
6. `scripts/run_all_tests.sh` 完整通过。
7. `npm pack --dry-run` 通过并产生可解析的包信息。
8. `cargo publish --dry-run --manifest-path rust/Cargo.toml` 通过。
9. Go module 可在临时消费者模块中按 `/v3` 编译。
10. npm、crates.io 和远端 Git 中不存在本次目标版本或目标 tag。
11. `npm`、`cargo`、`git` 认证状态可用。
12. 本次需要的所有命令均存在；缺失任何命令直接失败。

不得把“版本不存在”与“无法访问 registry”混为一类：

- registry 明确返回不存在，才允许继续。
- DNS、超时、认证、限流或未知响应必须直接失败。

## 8. 发布动作顺序

全部前置检查通过后，发布脚本按固定顺序执行：

1. 在本地为当前 HEAD 创建 Go tag `v${packages.go}`。
2. 在本地为当前 HEAD 创建 Rust tag `rust-v${packages.rust}`。
3. 发布 npm 包。
4. 发布 Rust crate。
5. 原子推送两个 tag；若 Git 服务不支持原子 tag push，脚本必须在前置检查阶段直接失败，不能退化为逐个 push。
6. 使用公开代理验证 `github.com/bsv8/MultisigPool/v3@v${packages.go}` 可解析。
7. 验证 npm registry 返回本次 npm 版本。
8. 验证 crates.io 返回本次 Rust 版本。

脚本完成时打印中文发布摘要，但所有错误消息必须使用英文。

GitHub Release 不属于三语言包发布的必要条件。本次应从统一发布脚本中删除 `gh` 可选分支；如需 GitHub Release，另立明确、强制依赖 `gh` 的施工单，不能在缺少工具时跳过后仍宣称全部发布完成。

## 9. 外部发布无法原子化的特殊处理

npm、crates.io 和 Git/Go proxy 不支持跨平台事务。一旦第一个 registry 接受版本，无法回滚或覆盖。因此必须预先定义中断规则。

### 9.1 尚未有任何外部发布成功

- 删除本次脚本创建但尚未推送的本地 tag。
- 暴露原始错误并退出。
- 修复问题后仍使用同一清单重新执行完整发布。

本地 tag 清理只能针对脚本刚创建且仍指向当前 HEAD 的两个精确 tag；目标不满足时不得删除。

### 9.2 npm 已成功，Rust 尚未成功

- 不得更换 npm、Go 或 Rust 版本。
- 不得重新发布或覆盖 npm 包。
- 使用同一个入口显式执行：

```bash
scripts/release-all.sh --resume-from rust
```

- 恢复模式必须验证 npm registry 中的版本、包名、Git commit 标识和本地预构建包完整性一致，然后才允许继续。
- 任一验证不可完成时直接失败，不得假设已发布包正确。

### 9.3 npm 与 Rust 已成功，tag 推送失败

显式执行：

```bash
scripts/release-all.sh --resume-from tags
```

恢复模式必须验证两个 registry 版本与当前 HEAD 一致，并验证本地 tag 精确指向当前 HEAD。远端已存在的 tag 只有在同样指向当前 HEAD 时才视为已完成；指向其他提交必须直接失败。

### 9.4 tag 已推送但 Go proxy 尚不可解析

显式执行：

```bash
scripts/release-all.sh --resume-from verify
```

该模式只执行三种产物的严格验证，不重复 publish，不创建新版本，不自动等待，不循环重试。代理尚未同步时明确失败，由操作者稍后再次执行同一验证命令。

### 9.5 恢复模式共同规则

- 恢复动作仍然只有 `release-all.sh` 一个公开入口。
- 必须由操作者显式指定恢复点，不得自动猜测或静默跳过步骤。
- 必须重新执行版本一致性检查和完整测试门禁。
- 必须验证 HEAD 与首次发布时的 commit 完全相同。
- 不允许 `--force`、覆盖 tag、撤销已发布包或用新版本掩盖失败。

## 10. 不能怎么做

- 不能保留多个具有发布能力的脚本。
- 不能从命令行参数或交互输入临时指定与清单不同的版本。
- 不能让 npm、Go、Rust 各自读取不同的人工版本来源。
- 不能在发布脚本中使用 `|| true`、默认版本、失败后继续或缺少工具时跳过。
- 不能允许非 `main` 分支人工确认后继续。
- 不能自动执行 `git commit`、修改业务文件或推送 `main`；版本同步应先作为普通代码变更审查并提交。
- 不能发布脏工作树、暂存区有内容或含未跟踪文件的状态。
- 不能先发布后测试。
- 不能用扩大静态扫描忽略规则掩盖旧入口。
- 不能在 npm 发布后改用新版本继续 Rust 或 Go 发布。
- 不能删除、重打或强推已经存在的远端 tag。
- 不能把 registry 暂时不可访问解释为“版本不存在”。
- 不能运行时依赖仓库外部的 `release/versions.json`；版本应在构建时生成进各语言产物。

## 12. 测试要求

### 12.1 版本同步单元测试

至少覆盖：

- 合法清单可生成确定内容。
- 缺失任何字段会失败。
- 未知字段会失败，防止拼写错误被忽略。
- 协议版本不是整数会失败。
- 任一包版本不是完整 SemVer 会失败。
- npm、Go 与 Rust 任意版本不一致都会失败。
- Go module major 与 `/v3` 不一致会失败。
- `package.json`、lock、Cargo、Go、TypeScript 任一镜像被篡改后 `check` 会失败。
- 目标字段出现零次或多次会失败。
- 错误消息全部为英文。
- `check` 不修改任何文件。
- 两次 `sync` 结果完全相同。

### 12.2 发布计划测试

发布逻辑中的版本解析、tag 推导、步骤选择和恢复计划必须提取为纯函数，并在不访问真实 registry 的测试中覆盖：

- 正常发布步骤顺序固定。
- 非 main 分支失败。
- 脏工作树失败。
- HEAD 未推送失败。
- tag 已存在失败。
- npm 或 Rust 版本已存在时正常发布失败。
- registry 不可访问时失败，不能当作版本不存在。
- `--resume-from rust` 只在 npm 产物验证一致时继续。
- `--resume-from tags` 只在两个 registry 产物一致时继续。
- `--resume-from verify` 不产生外部写操作。
- 未知恢复点失败。
- 不存在自动跳过、默认值或隐式重试。

### 12.3 现有协议回归

版本施工不得改变交易协议字节。必须继续通过：

- TypeScript 测试、lint、ESM/CJS/DTS build。
- Go vet、test 和示例编译。
- Rust fmt、locked test、clippy。
- 2-of-2 Go/TypeScript 字节对比。
- 2-of-3 Go/TypeScript 全三种签名组合字节对比。
- Rust/Go Step1–Step5 字节对比。
- offline 示例完整运行。
- online 示例只编译，不在门禁中访问真实网络或广播。

## 13. 一次性施工顺序

以下是同一迭代内部的依赖顺序，不代表分阶段交付：

1. 新增版本清单 schema、解析和纯校验测试。
2. 新增 Go/TypeScript 生成版本文件，并让所有公共常量改用统一来源。
3. 同步 npm、Go、Rust 当前版本镜像及锁文件。
4. 把版本 `check` 加入完整门禁首项。
5. 新增唯一 `release-all.sh` 及发布计划/恢复模式测试。
6. 删除三个旧发布脚本和所有旧 package scripts、文档入口。
7. 更新 README、PACKAGING、Rust 文档和原角色施工单引用。
8. 执行完整验收并确认协议交易字节零变化。
9. 将全部改动一次性暂存、审查和提交；不得提交一半入口或一半版本来源。

## 14. 最终验收清单

### 14.1 唯一事实源

- [ ] 仓库只有 `release/versions.json` 可以人工指定协议与包版本。
- [ ] 协议版本 `3` 与各包发布版本含义明确分离。
- [ ] npm/Go/Rust 镜像与清单完全一致。
- [ ] Go module `/v3` 与 Go tag 主版本一致。
- [ ] Rust tag 不与 Go tag 冲突。
- [ ] 生成文件相同输入产生相同字节。
- [ ] 任何镜像不一致都会在完整门禁第一阶段失败。

### 14.2 唯一发布入口

- [ ] 只有 `scripts/release-all.sh` 具有发布能力。
- [ ] `package.json` 只有一个 `release` 命令。
- [ ] 三个旧发布脚本和旧 package scripts 已删除。
- [ ] 文档中不存在旧发布命令。
- [ ] 发布脚本不接受临时版本输入，不自动修改版本文件。
- [ ] 正常发布和三种恢复模式都使用同一个入口。

### 14.3 严格失败

- [ ] 非 main、脏工作树、未推送 HEAD、缺少工具、缺少认证均立即失败。
- [ ] registry 网络错误不会被解释为版本不存在。
- [ ] 不存在 `|| true`、默认版本、自动猜测、自动重试或交互确认后继续。
- [ ] 所有错误消息为英文。
- [ ] 所有用户说明、文档和正常状态输出为中文。
- [ ] 缺少 `gh` 不再形成退化路径，因为 GitHub Release 不属于本脚本。
- [ ] tag 冲突或指向错误提交时绝不覆盖。

### 14.4 发布完整性

- [ ] 第一次外部写入前，版本检查、完整测试和两种包 dry-run 已全部通过。
- [ ] npm 包、Rust crate 和两个 Git tag 都能关联到同一个 Git commit。
- [ ] npm/Go/Rust 发布版本与清单完全一致。
- [ ] npm 与 crates.io 已存在目标版本时，正常发布会失败。
- [ ] Go tag 推送后 module proxy 可解析对应 `/v3` 版本。
- [ ] 中途失败只允许按原版本、原 commit 显式恢复。
- [ ] 发布脚本成功退出时，三语言产物均已验证可获取。

### 14.5 协议回归

- [ ] `scripts/run_all_tests.sh` 通过。
- [ ] Go、TypeScript、Rust 格式、静态检查和测试通过。
- [ ] 2-of-2、2-of-3 和三种仲裁签名组合字节不变。
- [ ] fixture 的协议仍为 `bitfs.pool.v3` / `3`。
- [ ] 本施工未引入 v2 兼容、角色别名、自动识别或其他兜底路径。
- [ ] 工作树与暂存区同步，`git diff --check` 和生成文件检查通过。

## 15. 完工判定

只有当第 14 节全部通过，仓库中只剩一个人工版本事实源和一个公开发布入口，并且现有 v3 交易字节完全不变时，本次施工才算完成。

以下状态均不算完成：

- 版本清单已经存在，但某个语言仍能独立修改版本且门禁不报错。
- 统一脚本已经存在，但旧发布脚本仍可执行。
- 三个包都能发布，但无法证明来自同一 commit。
- npm 已发布而 Git tag 或 Rust crate 使用了不同版本/提交。
- 发布失败后自动跳过、换版本或继续宣称完成。
- 为方便发布而把协议版本和包版本重新合并为同一字段。
